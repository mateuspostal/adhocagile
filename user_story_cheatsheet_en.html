User Story Anatomy
Como [quem], quero [o quê], para que [por quê / benefício].
A User Story is not a technical requirement — it is a conversation about value between the team and the user
As [who]
Persona or role
Who will benefit from the feature. Must be a real role, not generic. The more specific, the easier to prioritize.
✓ "gerente de produto" ✗ "usuário"
✓ "cliente cadastrado" ✗ "sistema"
I want [what]
Action or capability
What the user needs to do or have. Must be a user action, not a technical implementation. No "should", no passive voice.
✓ "filtrar tarefas por status" ✗ "um endpoint de filtros"
✓ "receber notificação" ✗ "ser notificado"
So that [why]
Benefit or outcome
The value or outcome expected by the user. It is the most important element — defines the "why" of the story and guides the team toward the solution.
✓ "não perca prazos importantes" ✗ "para ver as tarefas"
✓ "reduza o tempo de revisão" ✗ "para usar o sistema"
✓ Well-written example
As a project manager, I want to view the status of all sprint tasks in a single dashboard, so that I can identify blockers without having to ask each team member individually.
✗ Poorly written example
The system shall display a dashboard screen with all sprint tickets and their respective statuses updated in real time via WebSocket.
✗ No user · ✗ No benefit · ✗ It is a technical specification, not a story
Hierarchy — Epic · Feature · Story · Task
🗺️
Épico
Months · Big objective
Large business initiative grouping several related features. Too large to fit in a single sprint.
"App payment system"
›
📦
Feature
Weeks · Functionality
User-deliverable value functionality. Fits in 1–3 sprints. Groups stories from the same flow.
"Credit card checkout"
›
📝
User Story
1 sprint · User value
Unit of work deliverable in 1 sprint. Written from the user's perspective. Has acceptance criteria.
"As a customer, I want to enter my card..."
›
🔧
Task
Hours · Technical
Technical sub-task to implement the story. Created by devs during sprint planning. Has no direct user value.
"Create POST /payments endpoint"
›
🐛
Bug / Spike
Variable · Special
Bug: unexpected behavior in production. Spike: technical investigation with a defined timebox.
Spike: "Research PDF libraries — max 4h"
INVEST — User Story quality checklist
I
Independent
The story must not have strong dependency on another story. It should be developed and delivered in isolation.
"Can I do this story without finishing another one first?"
N
Negotiable
It is not a rigid contract. The solution can be negotiated between PO and team. The story captures the conversation, not a fixed specification.
"Can the team propose a different solution?"
V
Valuable
Delivers real value to a user or the business. Each story must have a clear "so that". Technical stories need their value explained.
"Who benefits and how?"
E
Estimable
The team must be able to estimate the effort. If they can't, clarity is missing or the story is too large. A Spike can help make it estimable.
"Can the team give an estimate?"
S
Small
Must fit in 1 sprint. Ideal: completable in 2–3 days. If larger, split it. Large stories increase the risk of not delivering in the sprint.
"Can the team finish it in the sprint?"
T
Testable
Must have clear acceptance criteria that allow verifying whether it was implemented correctly. If it cannot be tested, it is not ready.
"How do we know it's done?"
Acceptance Criteria — two formats
📋
List Format — Rules Checklist
Simpler. Ideal for stories with clear business rules. Each item is verifiable as true/false.
US: Filter tasks by status
The user can select one or more statuses (To do, In progress, Done)
The list updates instantly when the filter is applied
With no filter selected, all tasks are displayed
The filter persists when navigating away and returning
Displays the filtered task count at the top of the list
Must not reload the entire page when filtering
✓ Simple to write · ✓ Easy to use as QA checklist · ✗ May omit alternative flows (error paths)
🧪
BDD Format — Given/When/Then Scenarios
More powerful. Ideal for flows with multiple paths (happy path + edge cases). Foundation for automated tests.
US: Filter tasks by status
Scenario 1 — Filter with results
Given  the user is on the tasks screen
When   selects the "In progress" filter
Then   sees only tasks with "In progress" status
And    the count displayed matches the total filtered
Scenario 2 — Filter with no results
Given  no tasks are "Blocked"
When   selects the "Blocked" filter
Then   sees the message "No tasks found"
✓ Covers happy path and edge cases · ✓ Automatable with Cucumber/Gherkin · ✗ More effort to write
Given
Dado que
Initial context. System state before the action.
When
Quando
Action performed. What the user does or what happens.
Then
Então
Expected outcome. What must be observable after the action.
And / But
E / Mas
Continues the previous context. Avoids repeating Given/When/Then.

How to split a large story — 6 splitting patterns
🔀 By workflow
Separate the happy path from alternative and error paths.
Single US: "Do checkout with card"
US 1: Checkout with valid card (happy path)
US 2: Error message with invalid card
US 3: Retry after processing failure
📊 By business rule
Each rule variation becomes a separate story.
Single US: "Calculate order discount"
US 1: Discount for VIP customer (15%)
US 2: Discount by promo code
US 3: Discount on purchases over $200
🎭 By role (persona)
Different users have different experiences of the same feature.
Single US: "Manage system users"
US 1: Admin creates and edits users
US 2: Manager views users in their area
US 3: User edits their own profile
📱 By platform / channel
Desktop and mobile versions can be separate stories.
Single US: "Receive notifications"
US 1: Email notification
US 2: Push notification on mobile app
US 3: Slack notification
⭐ By data priority
Deliver with a subset of fields and expand later.
Single US: "Create complete user profile"
US 1: Create profile with name and email (MVP)
US 2: Add photo, bio and social networks
US 3: Advanced preferences and privacy
📈 By performance / quality
Deliver working first, with performance as a separate story.
Single US: "Ultra-fast real-time search"
US 1: Functional search (result in <3s)
US 2: Optimize search to <500ms
US 3: Search with autocomplete and suggestions
Definition of Done (DoD) — when a story is truly done
💻 Development
Code reviewed (code review)
Unit tests written and passing
Code coverage ≥ 80%
No critical lint warnings
No new technical debt introduced
🧪 Quality
Integration tests passing
All acceptance criteria verified
Tested in staging with real data
No critical or blocking bugs open
Basic accessibility verified
🚀 Delivery
Staging deploy completed successfully
CI/CD pipeline green
Feature flag configured (if applicable)
Rollback plan defined
Validated by PO in staging
📚 Documentation
Ticket updated with decisions made
ADR created (if architectural change)
API documented (if new endpoint)
Knowledge base updated
Sprint review notified about delivery
⚡ DoD vs. Acceptance Criteria: Acceptance Criteria are specific to each story ("the filter works X way"). The Definition of Done is the team's global standard that every story must meet before closing — regardless of the story.
Common mistakes — and how to fix them
⚠️
Technical story disguised as a US
"As a system, I want a REST endpoint to return the task list in JSON"
"As a manager, I want to see all open tasks of my team so I can prioritize the week's work"
⚠️
Vague acceptance criterion
"The system should be fast and intuitive"
"Screen loads in less than 1.5s · User completes the action in at most 3 clicks"
⚠️
Story without a real "so that"
"As a user, I want an export button so that I can export"
"As an analyst, I want to export data as CSV so I can cross-reference with other spreadsheets in my area"
⚠️
Never-ending story (disguised epic)
"As a user, I want to manage my profile completely with photo, bio, preferences and history"
Split: Story 1: edit name and email · Story 2: photo upload · Story 3: notification preferences
